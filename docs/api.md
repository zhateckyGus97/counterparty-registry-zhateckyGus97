# HTTP API

После локального запуска Swagger UI доступен по http://localhost:5080/swagger, OpenAPI-документ — /swagger/v1/swagger.json. Корень / перенаправляет в Swagger. Для удобства проверки тестового Swagger включён независимо от окружения.

## Маршруты

| Метод | Путь | Результат |
| --- | --- | --- |
| GET | /api/clients?page=1&pageSize=20&type=LegalEntity | 200: страница клиентов |
| GET | /api/clients/{id} | 200: карточка со всеми учредителями |
| POST | /api/clients | 201: созданный клиент и Location его карточки |
| PUT | /api/clients/{id} | 200: изменённая карточка |
| DELETE | /api/clients/{id} | 204: клиент и его связи удалены, общие учредители сохранены |
| POST | /api/clients/{id}/founders/{founderId} | 200: карточка с новой связью |
| DELETE | /api/clients/{id}/founders/{founderId} | 200: карточка после удаления связи |
| GET | /api/founders?page=1&pageSize=20 | 200: страница учредителей |
| GET | /api/founders/{id} | 200: учредитель |
| POST | /api/founders | 201: созданный учредитель и Location |
| PUT | /api/founders/{id} | 200: изменённый учредитель |
| DELETE | /api/founders/{id} | 204: удалён учредитель без связей |

Размер страницы — от 1 до 100, номер начинается с 1. Type в списке клиентов необязателен. Списки отсортированы по CreatedAt DESC, затем Id DESC. Offset-пагинация не обеспечивает снимок набора данных при параллельных изменениях.

PUT заменяет все редактируемые поля карточки. Для изменения типа нужно передать соответствующий ему ИНН. Учредители редактируются отдельными операциями. Повторное добавление связи возвращает 409. Удаление отсутствующего объекта возвращает 404, отсутствующей связи — 409.

## Пример проверки через Swagger

1. POST /api/clients:

```json
{
  "inn": "7701234560",
  "name": "ООО Альфа",
  "type": "LegalEntity"
}
```

2. POST /api/founders:

```json
{
  "inn": "123456789047",
  "fullName": "Иванов Иван Иванович"
}
```

3. Скопируйте id из двух ответов и вызовите POST /api/clients/{id}/founders/{founderId}. Тело запроса не требуется.
4. GET /api/clients/{id} вернёт общие сведения учредителя и дату создания связи. Дата создания самого учредителя находится внутри founder.
5. Попробуйте повторно добавить связь — получите 409 и code client.founder_already_linked.

Для ИП используйте type IndividualEntrepreneur и корректный 12-значный ИНН. Тип в JSON передаётся строкой, числовые значения не принимаются. В query-параметре type рекомендуется также использовать имя типа. ИНН в примерах подобраны для проверки контрольной суммы; существование этих номеров в реестре не подтверждается.

Изменение ФИО учредителя влияет на карточки всех связанных компаний. Оно не обновляет Client.UpdatedAt; добавление и удаление связи обновляет эту дату. Все даты возвращаются в UTC.

## Ошибки

Ошибки возвращаются как application/problem+json:

```json
{
  "type": "about:blank",
  "title": "Конфликт данных",
  "status": 409,
  "detail": "Клиент с таким ИНН уже существует.",
  "instance": "/api/clients",
  "code": "client.inn_conflict",
  "traceId": "идентификатор запроса"
}
```

Ошибки полей дополнительно содержат errors со списками сообщений. До вызова сервиса ASP.NET Core проверяет формат запроса, обязательные поля, значения enum, пагинацию и пустой Guid. Проверки контрольных цифр ИНН, его длины для типа клиента и длины названия / ФИО выполняет Domain. В обоих случаях ответ — 400 с code validation_error. Domain сообщает первую найденную ошибку поля; ASP.NET Core может вернуть несколько ошибок сразу. Некорректный формат Guid в пути не совпадает с маршрутом и даёт 404.

Соответствие ошибок:

- 400: некорректный запрос или DomainValidationException; code validation_error.
- 404: отсутствующий объект или маршрут; code not_found.
- 409: ConflictException или DomainRuleException; сохраняется их Code. Конкурирующее сохранение даёт concurrency_conflict.
- 405: неподдерживаемый HTTP-метод.
- 415: неподдерживаемый Content-Type тела запроса.
- 500: неожиданная ошибка; code internal_error. Детали и стек остаются в серверном логе.

ArgumentException не превращается автоматически в 400: он может означать ошибку реализации. Для ошибок редактируемых полей Domain использует отдельный DomainValidationException с FieldName и сообщением. ApiExceptionHandler преобразует его в ValidationProblemDetails. Нарушения правил, зависящих от состояния объекта, представлены DomainRuleException и дают 409.

ApiExceptionHandler обрабатывает исключения централизованно. Логирование ExceptionHandlerMiddleware отключено только для устранения дублирования: известные отказы пишет ApiExceptionHandler с кодом и traceId, неожиданные — с исходным исключением. Тела запросов не логируются.

## Структура API

- Controllers: HTTP-маршруты и вызовы IClientService / IFounderService.
- Models: входные HTTP-модели и параметры списков. Они отделены от Application, чтобы атрибуты ASP.NET Core не попадали в сценарии приложения.
- Validation: проверка непустого Guid в параметрах маршрута.
- ErrorHandling: централизованная обработка исключений.
- Program: регистрация зависимостей, JSON, Swagger и middleware.

Входные модели не повторяют проверки ИНН и длины из Domain. Required и EnumDataType описывают обязательность и допустимые значения HTTP-полей; сущность также защищает себя при вызове из других точек входа. В Application передаются обычные Create/Update-запросы. Контроллер не работает с DbContext и не вызывает SaveChanges.

## Проверка

HTTP-тесты запускают настоящий pipeline через WebApplicationFactory с изолированной SQL Server БД. Это интеграционные тесты без отдельного TCP-порта. Тестовые endpoints, выбрасывающие исключения, добавляются только тестовой фабрикой и отсутствуют в обычном приложении.

После подготовки Docker и переменных среды: `dotnet test CounterpartyRegistry.sln`.

Аутентификация, интеграции с внешними реестрами, ETag/If-Match и публикация приложения не реализованы: они не входят в текущий CRUD-контракт. SQL rowversion защищает изменения внутри серверного сценария, но пока не сравнивается с версией карточки на стороне пользователя.
