# SQL Server: локальный запуск и устройство Infrastructure

## Запуск из PowerShell

Из корня репозитория, при запущенном Docker Desktop в режиме Linux containers:

```powershell
. ./scripts/Use-LocalDatabase.ps1
docker compose up -d --wait sqlserver
dotnet tool restore
dotnet ef database update --project src/CounterpartyRegistry.Infrastructure --startup-project src/CounterpartyRegistry.Api
dotnet run --project src/CounterpartyRegistry.Api --no-launch-profile --urls http://localhost:5080
```

Первая точка в `. ./scripts/Use-LocalDatabase.ps1` означает выполнение в текущей PowerShell-сессии. Скрипт формирует переменную окружения ConnectionStrings__DefaultConnection и сохраняет эту же строку в User Secrets проекта Api. Значение передаётся dotnet через stdin, не печатается в терминал и не записывается в репозиторий.

Профили http / https в Visual Studio используют Development и автоматически читают User Secrets. После однократного выполнения скрипта можно остановить предыдущую отладку и запускать Api по F5 без зависимости от терминала. Production-запуск без launch profile по-прежнему использует переменную окружения; в новом терминале для него нужно снова выполнить скрипт. После изменения порта или пароля в .env повторите скрипт, чтобы синхронизировать настройки.

При отсутствии .env скрипт создаёт его со случайным паролем. При повторном запуске использует прежний файл. .env игнорируется Git, .env.example описывает его формат. Простой загрузчик рассчитан на строки KEY=value без кавычек и подстановок. Сгенерированный пароль соответствует этому формату; специальные символы dotenv при ручной настройке нужно учитывать отдельно.

Контейнер содержит SQL Server. Приложение запускается на Windows через dotnet, его образ на этом этапе не создаётся. Маршрут GET / перенаправляет в Swagger; CRUD-контроллеры подключены. Примеры запросов находятся в api.md.

## Что делает Compose

`compose.yaml` описывает сервис sqlserver:

- image: готовый образ Microsoft SQL Server 2022 для Linux. При первом запуске Docker скачивает слои образа. Тег 2022-latest обновляемый; в воспроизводимом окружении можно зафиксировать проверенный digest.
- ACCEPT_EULA=Y: принятие лицензии образа; MSSQL_PID=Developer: редакция для разработки и тестирования.
- MSSQL_SA_PASSWORD: начальный пароль администратора SQL Server из локального .env. Для разработки приложение подключается под sa; для развёртывания нужен отдельный пользователь с ограниченными правами.
- ports: 127.0.0.1:14333 на компьютере перенаправляется в 1433 внутри контейнера. Приложение подключается по tcp:127.0.0.1,14333 явно через IPv4; это исключает неоднозначность localhost / IPv6. SQL_PORT в .env позволяет изменить внешний порт. Соседний контейнер подключался бы к sqlserver,1433 по имени сервиса.
- volumes: именованный том sqlserver-data подключён к /var/opt/mssql. В нём находятся данные SQL Server, включая базы. Фактическое имя тома имеет префикс проекта counterparty-registry.
- healthcheck: sqlcmd выполняет SELECT 1 внутри SQL Server. Состояние running ещё не гарантирует готовность БД, а healthy означает, что проверка прошла. --wait ожидает готовности сервиса.

TrustServerCertificate=True в локальной строке подключения позволяет работать с сертификатом SQL Server из контейнера. Настройку подключения и учётные данные для развёртывания следует задавать отдельно.

Переменная среды внутри healthcheck записана с двумя знаками доллара: $$MSSQL_SA_PASSWORD. Так Compose оставляет подстановку оболочке внутри контейнера, а не выполняет её при чтении YAML.

## Контейнер и данные

Полезные команды:

```powershell
docker compose ps
docker compose logs --tail 50 sqlserver
docker compose stop sqlserver
docker compose start sqlserver
```

stop останавливает процесс SQL Server; start запускает тот же контейнер снова. `docker compose down` удаляет контейнер и сеть проекта, сохраняя именованный том. Следующий up создаст контейнер заново и подключит прежние данные.

Команда `docker compose down -v` удаляет и том с базами. Это сброс данных, выполнять его следует только при намерении удалить локальную БД. Для обычного завершения работы достаточно stop или down.

Изменение MSSQL_SA_PASSWORD в .env не меняет пароль уже существующего SQL Server в сохранённом томе. Пароль меняют средствами SQL Server; пересоздание пустого тома допустимо только при намеренном сбросе локальных данных. Храните .env вместе с локальным окружением, не публикуя его.

## Миграции

Compose запускает SQL Server, но не создаёт таблицы приложения. Их создаёт `dotnet ef database update`, применяя миграции из Infrastructure. EF хранит перечень выполненных миграций в __EFMigrationsHistory, поэтому повторный вызов не создаёт таблицы заново.

Миграции не запускаются автоматически при старте API. Это отдельный явный шаг. Для последующего изменения модели:

```powershell
dotnet ef migrations add MeaningfulChangeName --project src/CounterpartyRegistry.Infrastructure --startup-project src/CounterpartyRegistry.Api --output-dir Persistence/Migrations
```

Просмотрите созданный код перед database update. Локальный инструмент dotnet-ef зафиксирован в dotnet-tools.json; dotnet tool restore устанавливает указанную версию.

## Как устроен Infrastructure

- RegistryDbContext реализует IUnitOfWork. Все репозитории в одном DI scope используют этот же экземпляр. SaveChangesAsync сохраняет изменения общей транзакцией. PrepareClientVersionUpdates обеспечивает обновление rowversion клиента при изменении связей, а PersistenceExceptionTranslator преобразует известные ошибки БД в ConflictException, сохраняя исходное исключение. Неизвестные ошибки пробрасываются без преобразования. SaveChanges и SaveChangesAsync используют одинаковые подготовку и обработку ошибок; Application вызывает асинхронный вариант.
- ClientRepository загружает полную коллекцию связей и общих учредителей для изменения карточки. Списки выполняются отдельными проекциями с пагинацией, без загрузки графа и без tracking.
- FounderRepository работает с общим справочником и проверяет наличие связей.
- Configurations задают таблицы Clients, Founders и ClientFounders, ограничения длины и формата, уникальные ИНН, составной ключ связи и внешние ключи. _founderLinks используется как backing field: Domain сохраняет закрытую коллекцию.
- Удаление клиента каскадно удаляет связи. Удаление связанного учредителя блокируется внешним ключом. Проверка в сервисе обеспечивает понятную раннюю ошибку, а БД защищает от конкурентного изменения.

В таблицах Clients и Founders есть SQL Server rowversion. Это служебная версия строки, не дата. Она настроена как shadow property EF, поэтому в Domain не появляется свойство, относящееся к технологии хранения. Устаревшее изменение обнаруживается при сохранении и преобразуется в ConflictException.

Изменение участия также принудительно помечает Client.UpdatedAt изменённым в EF. Это обеспечивает обновление rowversion даже при совпавшем времени. Иначе одновременная смена типа клиента и добавление учредителя могли бы нарушить правило ИП без учредителей. Если возникает конфликт, откатывается вся транзакция, включая добавление связи.

Обрабатываются только известные уникальные индексы и внешние ключи. Остальные ошибки БД не маскируются под пользовательские конфликты. Исходное исключение сохраняется как InnerException.

rowversion сейчас обнаруживает конкуренцию между загрузкой сущности и сохранением в сценарии сервиса. Это ещё не защита от редактирования устаревшей карточки в браузере: для неё позже потребуется передавать клиентскую версию (например, ETag / If-Match).

## Тесты

Unit-тесты не требуют Docker:

```powershell
dotnet test tests/CounterpartyRegistry.UnitTests
```

Интеграционные тесты используют запущенный SQL Server из Compose:

```powershell
. ./scripts/Use-LocalDatabase.ps1
docker compose up -d --wait sqlserver
dotnet test tests/CounterpartyRegistry.IntegrationTests
```

Тесты создают отдельную базу с именем CounterpartyRegistryTests_<случайный суффикс>, применяют настоящие миграции, выполняют проверки и удаляют только эту базу. Рабочую CounterpartyRegistry не очищают. Проверяются сохранение и загрузка графа, CRUD через сервисы, пагинация, индексы, внешние ключи, удаление связей, транзакции и конкурирующие операции.

После подготовки окружения можно выполнить все тесты: `dotnet test CounterpartyRegistry.sln`.
