# Доменная модель

## Границы и допущения

Domain содержит сущности и правила их изменения, не зависит от EF Core, SQL Server, ASP.NET Core или библиотек валидации. Создание и изменение проходят через методы сущностей; свойства имеют закрытые setters. Наследуемые базовые сущности и механизмы доменных событий пока не нужны.

Клиент — юридическое лицо или ИП. Учредитель в рамках задания считается физическим лицом, поскольку для него требуется ФИО. ИНН учредителя состоит из 12 цифр. Поддержку учредителей-организаций следует добавлять отдельным изменением модели и контрактов, если появится такое требование.

## Сущности и связь

- `Client`: Id, Inn, Name, Type, CreatedAt, UpdatedAt, FounderLinks.
- `Founder`: Id, Inn, FullName, CreatedAt, UpdatedAt.
- `ClientFounder`: ClientId, FounderId, Founder, CreatedAt. Идентичность связи задаётся парой ClientId + FounderId, отдельный Id ей не требуется.

Client и Founder имеют независимую идентичность и жизненный цикл. Связь относится к клиенту: создавать и удалять её можно через Client.AddFounder / RemoveFounder. Общий Founder можно использовать в нескольких клиентах. Изменение его данных действует для всех связанных компаний.

Оба вида клиента могут существовать без связей. У ИП учредителей быть не может. Добавление того же Founder.Id повторно запрещено. Смена типа ЮЛ на ИП разрешается только после удаления всех связей и с корректным 12-значным ИНН. Смена ИП на ЮЛ также требует ИНН соответствующего формата. Это правила редактирования карточки, а не модель юридической реорганизации.

Удаление связи не удаляет учредителя и не затрагивает другие компании. При будущем удалении клиента хранилище должно удалить его связи, сохранив учредителей. Удаление связанного учредителя следует запретить до явного удаления его связей.

## Валидация и изменение

- ИНН хранится строкой и проверяется по длине, ASCII-цифрам и контрольным цифрам. Строки из одних нулей запрещены. Это локальная проверка номера, не подтверждение регистрации в ФНС.
- Name и FullName обязательны, ограничены 200 символами после Trim. ФИО не обязано состоять ровно из трёх слов. Пробелы внутри значения не изменяются.
- Create и Update используют одинаковые проверки. Проверки завершаются до изменения состояния, поэтому ошибка не оставляет частично изменённую сущность.
- Id и CreatedAt не изменяются при Update. Повторное обновление теми же нормализованными значениями не меняет UpdatedAt.
- Время передаётся вызывающим кодом (в будущем через TimeProvider) и приводится к UTC. Domain не обращается к системным часам.
- Добавление и удаление связи обновляют Client.UpdatedAt. Изменение общего Founder обновляет только Founder.UpdatedAt. Изменения карточки учредителя не вызывают массовое обновление дат всех клиентов.

Ошибки аргументов представлены ArgumentException / ArgumentOutOfRangeException. Конфликты состояния представлены DomainRuleException со стабильным Code: client.has_founders, client.founders_not_allowed, client.founder_already_linked, client.founder_not_linked. HTTP-коды к исключениям будут сопоставлены в API.

## Обязательства будущих слоёв

Это требования к следующему этапу, а не уже реализованные гарантии базы данных:

1. Уникальные индексы Clients.Inn, Founders.Inn и составной ключ ClientFounders(ClientId, FounderId). Отдельные объекты Founder с одинаковым ИНН Domain создать может: без доступа к хранилищу глобальную уникальность проверить нельзя. Application должен находить существующего учредителя, а БД — защищать от гонки запросов.
2. Внешние ключи связи, удаление связей вместе с клиентом и запрет удаления связанного учредителя.
3. Перед изменением клиента загрузить всю коллекцию FounderLinks. Частично загруженная коллекция не позволяет проверить смену типа и повторное добавление связи. Для изменения правил нужны идентификаторы связей; Founder-навигация загружается отдельно, когда нужны сведения о человеке.
4. Защитить параллельные изменения клиента (например, смену типа одновременно с добавлением учредителя) через optimistic concurrency SQL Server. Каждая операция изменения связи должна сохранять изменение Client в той же транзакции. Повторная попытка должна заново загрузить состояние и проверить правила.
5. Для EF Core настроить backing field _founderLinks, ключи и приватные конструкторы. SQL Server и миграции в текущем этапе не подключены.

## Расширение

Доля участия, дата вступления и выхода относятся к ClientFounder. Контактные данные относятся к Founder. Новые способы получения данных используют сценарии Application и правила Domain. Расширение связи до хранения истории потребует отдельного решения о ключах и уникальности активного участия.

## Проверка

Из корня решения: `dotnet test CounterpartyRegistry.sln`.

Тесты покрывают формат и контрольные цифры ИНН, обязательность и длину полей, нормализацию, UTC, обновления без частичной записи, смену типа клиента, общих учредителей, повторные связи, удаление связей и защиту коллекции от внешних изменений. Проверка EF mapping, уникальных индексов и конкурентных записей относится к будущим интеграционным тестам с SQL Server.
