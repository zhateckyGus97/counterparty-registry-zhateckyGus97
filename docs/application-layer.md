# Application: сценарии приложения

## 1. Контракты хранения — Abstractions

`IClientRepository` и `IFounderRepository` описывают конкретные операции над клиентами и учредителями. Они не возвращают IQueryable и не зависят от EF Core. Поэтому фильтрация, пагинация и детали запросов останутся в реализации Infrastructure.

`GetByIdAsync` возвращает изменяемую сущность, которая в реализации EF Core должна отслеживаться общим DbContext. Для клиента обязательна полная загрузка FounderLinks и связанных Founder: Domain проверяет коллекцию связей, а ответ содержит сведения об учредителях.

`GetPageAsync` возвращает готовую проекцию списка без отслеживания сущностей. Контракт предусматривает сортировку CreatedAt DESC, затем Id DESC. Сортировка нужна для однозначного порядка записей с одинаковой датой, но offset-пагинация не обеспечивает неизменность страниц при параллельном добавлении записей.

`Add` и `Remove` только подготавливают изменения. Они синхронные: регистрация изменения в DbContext сама по себе не выполняет SQL-запрос. `IUnitOfWork.SaveChangesAsync` сохраняет все подготовленные изменения.

## 2. Запросы и ответы — Clients и Founders

CreateClientRequest / UpdateClientRequest содержат Inn, Name и Type. CreateFounderRequest / UpdateFounderRequest содержат Inn и FullName. Id и даты создаёт сервер. Запросы — обычные records, без HTTP-атрибутов и зависимости от контроллеров.

Ответы ClientResponse и FounderResponse содержат копии значений. У них нет методов сущностей, и изменение загруженной сущности не меняет ранее сформированный ответ. В карточке клиента находятся сведения об учредителях и отдельная дата создания каждой связи.

Списки клиентов возвращают ClientSummaryResponse без вложенных учредителей. Это позволяет будущей реализации БД выполнять компактную проекцию вместо загрузки полного графа всех клиентов.

PageRequest проверяет номер страницы, размер от 1 до 100 и отсутствие переполнения Offset. PagedResult возвращает Items, TotalCount, PageNumber и PageSize. Номера страниц начинаются с 1.

## 3. Ошибки — Exceptions

- EntityNotFoundException: объект с указанным Id не найден; сохраняет EntityName и EntityId.
- ConflictException: конфликт с текущими данными; сохраняет стабильный Code.
- DomainRuleException: правило доменной модели нарушено; приходит из Domain без маскировки сервисом.
- DomainValidationException: ошибка редактируемого поля с FieldName; проверки выполняет Domain, сервис пропускает исключение без преобразования.
- ArgumentException: защитные проверки аргументов; проверки пустого Id и пагинации выполняет Application.

Application не назначает HTTP-коды. API сопоставляет ошибки с ProblemDetails: DomainValidationException даёт 400 с errors по полям, DomainRuleException и ConflictException — 409, EntityNotFoundException — 404. Нельзя безусловно считать любой ArgumentException из любой части приложения пользовательской ошибкой: формат запроса, пустые Id и пагинация проверяются на границе HTTP до вызова сервиса, а неожиданный ArgumentException даёт 500.

## 4. Сервисы — ClientService и FounderService

Сервисы находятся в папке Services и реализуют контракты IClientService и IFounderService из Abstractions. Clients и Founders содержат модели запросов и ответов. Папки сами по себе не меняют поведение приложения, но разделяют назначение файлов.

Сервисы организуют выполнение сценария. Бизнес-правила изменения собственных данных сущности остаются в Domain.

Сценарий ClientService.CreateAsync:

1. Проверить отмену запроса и наличие request.
2. Вызвать Client.Create: проверить и нормализовать поля, присвоить Id и даты. Время берётся через переданный TimeProvider.
3. Проверить занятость нормализованного ИНН через IClientRepository.
4. Вызвать Add — подготовить новую запись к сохранению.
5. Один раз вызвать IUnitOfWork.SaveChangesAsync.
6. После успешного сохранения сформировать ClientResponse.

```csharp
var client = Client.Create(request.Inn, request.Name, request.Type, timeProvider.GetUtcNow());
// Проверка занятости client.Inn через репозиторий.
clients.Add(client);
await unitOfWork.SaveChangesAsync(cancellationToken);
```

При редактировании проверка занятости ИНН исключает текущий Id и выполняется до изменения отслеживаемой сущности. Повторное сохранение собственного ИНН разрешено. Пустые значения и нарушения правил не обходят Domain.

ClientService предоставляет создание, получение карточки, список с фильтром по типу, изменение, удаление, добавление и удаление связи с учредителем. FounderService предоставляет CRUD учредителей и список. Все операции ввода-вывода получают CancellationToken вызывающей стороны.

Каждый успешный изменяющий сценарий вызывает SaveChangesAsync один раз; чтение не вызывает сохранение. Ошибки хранилища и отмена не преобразуются в успешный результат. Для Update без фактических изменений вызов сохранения допустим: Domain сохраняет прежний UpdatedAt, а EF Core сможет определить отсутствие изменений.

## 5. Общие учредители

Создание Founder и добавление его к клиенту — отдельные сценарии. AddFounderAsync принимает clientId и уже существующий founderId; копию человека для другой компании он не создаёт. Если ИНН уже занят, создание учредителя возвращает конфликт, а вызывающая сторона должна выбрать существующего учредителя (например, из списка) и использовать его Id.

Обновление Founder меняет общие сведения для всех компаний. Удаление Founder запрещено, пока существует хотя бы одна связь. RemoveFounderAsync удаляет только участие в указанном клиенте.

## 6. Что потребуется от Infrastructure и API

- Реализовать оба репозитория и IUnitOfWork через один scoped DbContext на запрос/сценарий. Интерфейс IUnitOfWork сам по себе не создаёт транзакцию. В EF Core её обеспечит один SaveChangesAsync для всех отслеживаемых изменений.
- Настроить уникальные индексы ИНН, ключи и внешние ключи связей. Предварительная ExistsByInnAsync улучшает сообщение об ошибке, но не защищает от гонки двух запросов.
- Переводить нарушения ожидаемых уникальных ограничений в ConflictException, сохраняя остальные ошибки БД как ошибки сервера. Между HasClientLinksAsync и удалением также возможна гонка; внешние ключи должны запретить удаление связанного учредителя.
- Настроить optimistic concurrency для конфликтующих изменений клиента и его связей. Ошибки сохранения не должны приводить к повторному использованию изменённого DbContext в другом сценарии.
- Реализовать удаление связей вместе с клиентом с сохранением общего Founder.
- Зарегистрировать IClientService → ClientService, IFounderService → FounderService и репозитории как scoped, TimeProvider.System — как источник времени. Контроллеры будут зависеть от интерфейсов сервисов и формировать HTTP-ответы.

SQL Server, транзакции, репозитории и регистрация DI реализованы в Infrastructure / Program. HTTP-контроллеры, входная валидация и преобразование ошибок в ProblemDetails реализованы в API. Порядок запуска описан в local-database.md, HTTP-контракт — в api.md.

При подключении API регистрация сервисов будет выглядеть так (потребуются using Abstractions и Services):

```csharp
builder.Services.AddScoped<IClientService, ClientService>();
builder.Services.AddScoped<IFounderService, FounderService>();
builder.Services.AddSingleton<TimeProvider>(TimeProvider.System);
```

Эта регистрация подключена в Program вместе с AddInfrastructure, который регистрирует репозитории и общий IUnitOfWork. DI означает передачу зависимостей извне и работает также с конкретными классами; интерфейсы нужны для явного контракта и подмены реализации.

## 7. Тесты

В tests/CounterpartyRegistry.UnitTests/Application находятся тесты сервисов и пагинации. ServiceTestContext заменяет хранилище тестовыми реализациями и считает вызовы сохранения; TestTimeProvider задаёт фиксированное время. Эти реализации проверяют оркестрацию и не имитируют транзакции или поведение EF Core.

Запуск из корня: `dotnet test CounterpartyRegistry.sln`.

Порядок чтения кода: IClientRepository → IUnitOfWork → ClientRequests → ClientResponses → ClientService.CreateAsync → ClientServiceTests. Затем можно разобрать обновление, связи и FounderService.
