# Автоматические проверки

GitHub Actions workflow: .github/workflows/ci.yml. Он запускается для pull request с целевой веткой master, после push в master (включая merge), а также вручную через workflow_dispatch. Push только в develop без открытого PR в master не запускает этот workflow.

Проверяется обычный PR merge commit, то есть результат объединения с целевой веткой, а не только исходная ветка. Для PR не используется pull_request_target. Токен workflow имеет только contents: read.

Job Build and test выполняет:

1. Checkout исходников и установку SDK .NET 8.
2. Создание global.json только внутри runner, чтобы выбрать .NET 8 среди предустановленных SDK. На локальный выбор SDK разработчика это не влияет.
3. Restore и сборку всего solution в Release.
4. Unit-тесты без повторной сборки.
5. Запуск SQL Server через compose.yaml с ожиданием healthy.
6. Интеграционные тесты, включая HTTP API. Отдельные тестовые базы создаёт SqlServerFixture, миграции применяются автоматически внутри fixture.
7. Сохранение TRX-отчётов в артефакт test-results на 7 дней, включая отчёты при падении тестов.
8. Логи SQL Server при ошибке и удаление CI-контейнера и его тома.

SQL Server использует временный пароль из workflow, который относится только к изолированному runner. Локальный .env, настройки разработчика и реальные учётные данные не нужны. Очистка с --volumes выполняется внутри CI; она не запускается на компьютере разработчика.

Новый запуск того же PR отменяет устаревший. Лимит job — 20 минут. При ошибке restore, сборки или тестов job становится красным, успешный статус не подменяется continue-on-error.

## Как включить

Workflow начнёт работать после коммита и push файла вместе с остальным исходным кодом и Compose. Пока Infrastructure, API и тесты остаются только в рабочей папке, удалённый runner не сможет их проверить. Для PR workflow должен присутствовать в проверяемых изменениях.

Результаты видны во вкладке Actions и в проверках pull request. Отчёты скачиваются из Artifacts соответствующего запуска.

Чтобы запретить merge при неуспешных тестах, настройте для master branch protection / ruleset с требованием успешного status check Build and test (от workflow CI). Сначала дайте workflow выполниться хотя бы один раз, чтобы проверка появилась в списке. Также обычно включают требование pull request и актуальности ветки относительно master. Доступность настроек зависит от типа репозитория и тарифа GitHub.

Сам workflow запускает тесты, но не создаёт правило защиты ветки. Настройки удалённого репозитория этим изменением не меняются.
